# Аудит безопасности и соответствия 152-ФЗ

Дата: текущая итерация (проект на стадии «начальная версия для тестового стенда»).
Назначение системы: проведение тестирования обучающихся методистами сети технопарков «Кванториум».

> Документ — технический аудит и чек-лист. Он не заменяет юридическую консультацию
> и оформление обязательных документов оператора ПДн (политика, согласия, уведомление РКН).

---

## 1. Модель угроз (кратко)

- **Акторы:** методисты (аутентифицированы, подтверждены админом), обучающиеся (без аккаунта,
  проходят тест по публичной ссылке), администратор.
- **Ценные данные:** учётные записи методистов (логин/пароль/ФИО/email/телефон), ПДн
  обучающихся (ФИО + номер сертификата ПФДО), результаты тестов, содержимое тестов.
- **Публичная поверхность:** страница прохождения теста по `public_token`, эндпоинты `/api/public/*`,
  `/api/auth/*`, статика.

---

## 2. Найденные проблемы

Приоритеты: **P0** — блокирует прод, **P1** — важно до реальных данных, **P2** — улучшение.

### P0. Обязательно исправить до публикации в интернет

1. **TLS терминируется на edge-прокси площадки, а не в контейнере.**
   Внутри контейнера nginx слушает только HTTP `:80` (`Dockerfile` → `EXPOSE 80`,
   `amvera.yml` → `containerPort: 80`, `docker/nginx.conf` → `listen 80;`). TLS
   снимает edge-прокси (на Amvera — Envoy), поэтому снаружи сайт открывается по
   **https**, а внутрь запрос идёт по HTTP. Это штатная схема «TLS termination на edge»;
   собственного TLS в `docker-compose` нет — это осознанно для локального стенда.
   - Что проверяется при выкладке (на уровне приложения не решается):
     - `cookie_secure=true` в переменных площадки — иначе `Secure`-флаг на JWT-cookie
       не ставится и токен уйдёт по HTTP. Дефолт в `config.py` — `true`;
     - редирект **http→https** включён на прокси (в контейнере его нет: внешняя схема
       известна только edge-прокси, приложение получает её через `X-Forwarded-Proto`).
   - Проверка: `GET /api/debug/ip` (только admin) отдаёт `x_forwarded_proto`,
     `cookie_secure` и все входящие заголовки; в браузере DevTools → Application →
     Cookies у `access_token`/`refresh_token` должен стоять флаг `Secure`.

2. **Ограничение попыток входа — реализовано частично.** `/api/auth/login` защищён лимитом
   (`services/ratelimit.py`): 5 неудач за 5 минут независимо по IP и по логину, блокировка
   с экспоненциальным ростом, `429` + `Retry-After`. Дополнительно: `register` (3 заявки/10 мин)
   и `public submit` (30 отправок/10 мин на `IP|public_token`).
   - Остаётся: rate limiting **in-memory** (один процесс, сбрасывается при рестарте);
     нужен Redis при масштабировании.

3. **Тестовый admin-пароль и секреты в открытом виде.** `.env` должен быть уникальным на проде,
   `admin_password` — сильным, `jwt_secret` — случайным ≥ 32 символов. Сейчас валидация есть
   (запрещает `admin12345`, требует `jwt_secret ≥ 32`), но значения по умолчанию в примере — заглушки.

### P1. Важно до обработки реальных ПДн

4. **Срок хранения ПДн — механизм есть, срок задаёт оператор.** По 152-ФЗ ПДн нельзя
   хранить дольше, чем нужно для цели.
   - Реализовано: фоновая задача `services/retention.py` (asyncio в `lifespan`) при старте
     и далее **раз в сутки** удаляет попытки старше `attempts_retention_days`;
     период проверки — `retention_check_interval_hours`.
   - **По умолчанию срок — 30 дней** (месяц), проверка раз в сутки. `0` выключает
     очистку полностью — это допустимо только осознанно, ПДн тогда хранятся бессрочно.
     Юридически подтвердите срок (например, 6–12 месяцев) и при необходимости выставьте
     своё значение переменной.
   - Удаляется попытка целиком (включая результаты) — политику хранения это должно учитывать.

5. **Согласие на обработку ПДн — реализовано для всех.** Методисты — при регистрации
   (`PdConsent` с версией и датой); обучающиеся — обязательный чекбокс на странице
   прохождения (`TakeTest`, не отмечен по умолчанию) со ссылкой на политику. Сервер
   отклоняет отправку без `participant.pd_consent` (`422`), факт/дата/версия
   фиксируются в `attempt.pd_consent` (`models/attempt.py`, `services/attempt_service.py`).
   - Остаётся: утвердить юридическую формулировку и актуальность версии (`pd_consent_version`).

6. **Номер сертификата ПФДО может быть ПДн.** Если он позволяет идентифицировать ребёнка вместе
   с ФИО — это персональные данные несовершеннолетних (особая категория по контексту).
   - Требуется: обработка по ст. 9 (согласие законного представителя для несовершеннолетних),
     минимизация, шифрование в покое (Mongo без шифрования диска по умолчанию).

7. **Нет журнала доступа к ПДн (аудит чтения).** Логируется только часть действий (`audit`).
   - Для полноты — логировать доступ к ФИО обучающихся, экспорту данных.

8. **Шифрование в покое.** MongoDB хранит данные в открытом виде на диске тома.
   - Требуется: шифрование диска/volume на уровне хостинга (LUKS, шифрованный volume).

### P2. Улучшения

9. **CSP и заголовки безопасности** на уровне приложения (частично настроены в nginx:
   `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`). Добавить Content-Security-Policy.

10. **Ограничение размера тела запроса** — настроено в nginx (`client_max_body_size 10m`).

11. **Логи содержат чувствительные данные?** Проверить, что в `logs/logs.txt` не пишутся пароли/токены.
    Сейчас `pymongo` пишет DEBUG с полными документами — **может содержать ПДн**. Рекомендуется на проде
    `logging` уровня WARNING (отключить `pymongo.*` DEBUG).

12. **Лишние зависимости** в `requirements.txt` (SQLAlchemy, alembic, Mako, Faker, opentelemetry) —
    не используются, увеличивают поверхность атаки и размер образа. Убрать.

    **Обновление: проверено `pip-audit` — 3 пакета с известными уязвимостями.**

    | Пакет | Версия | Уязвимостей | Исправлено в |
    |---|---|---|---|
    | `pillow` | 11.0.0 | 55 advisory | 12.3.0 / 13.0.0 |
    | `python-multipart` | 0.0.20 | 6 (DoS при разборе multipart) | 0.0.31 |
    | `dnspython` | 2.8.0 | 2 (зависимость pymongo) | 2.9.2 |

    Обновление версий требует проверки сборки образа — отдельная задача.
    `npm audit` по фронтенду: 0 уязвимостей.

13. **Дублирующиеся/временные файлы** в репозитории (`backend/*.json`, `*.bin`, `*.xlsx`, `*.txt`,
    `ck*.txt`, `cookies.txt`) — могли содержать данные. Удалить и добавить в `.gitignore`.

    **Обновление: `backend/openapi.json` в репозитории устарел** — в нём нет `/api/media`,
    `/api/admin`, полей `participant`/`captcha_*`. Контракт в файле расходится с кодом.
    Перегенерировать (`python -c "import main,json;json.dump(main.app.openapi(),open('openapi.json','w',encoding='utf-8'),ensure_ascii=False,indent=2)"`)
    или удалить из репозитория.

## 2a. Закрыто в текущей итерации

### Бомба декомпрессии при загрузке изображений (было P0)

Лимит в 5 МБ считался **по байтам**, а не по разрешению. Однотонная PNG 11000×11000
весит **117 КБ**, но при распаковке занимает сотни МБ: несколько таких файлов в одном
тесте исчерпывали память процесса. Pillow для таких размеров выдаёт только
`DecompressionBombWarning` (предупреждение), то есть файл **проходил** проверку.

- Исправление: `MAX_PIXELS = 24_000_000` в `services/media_service.py`; предупреждение
  Pillow превращается в исключение; отказ — по заголовку, до записи на диск.
- Покрыто: `tests/test_image_bomb.py` (бомба, порог Pillow, граница 24 Мп, анонимная загрузка).

### Перечисление логинов по времени ответа (было P1)

В `authenticate()` проверка пароля не выполнялась, если логин не найден
(`user is None or not verify_password(...)` — короткое замыкание), поэтому время ответа
выдавало, зарегистрирован ли аккаунт.

- Исправление: bcrypt сверяется **всегда**, для несуществующего логина — `security.stub_hash()`.
- Покрыто: `tests/test_user_service.py::test_authenticate_unknown_user_still_verifies`.

### Анонимная загрузка и владение файлом (подготовка к публичной странице)

`media.uploaded_by` допускает `None` (загрузка без аккаунта). Найден и закрыт дефект:
при `None` в поле и `user_id = None` в запросе сравнение «свой файл» проходило —
аноним мог удалять файлы без владельца.

- Исправление: `delete_media()` явно требует `user_id is not None` вне админа.
- Все проверки изображения живут в сервисе (`store_media()`), а не в роутере, поэтому
  публичная загрузка получит тот же конвейер без дублирования кода.
- **Что останется сделать при добавлении публичной загрузки:** квота по IP/`public_token`
  (место на диске), капча на загрузку, чистка «сирот», модерация анонимного контента.
  Подробности — `docs/architecture.md`, раздел 10.

## 3. Что уже сделано правильно

- Пароли — bcrypt-хэши (`passlib`), не в открытом виде.
- JWT в HttpOnly-cookie; доступ к токену из JS невозможен.
- Refresh-токен с ротацией и разделением по `type`-claim.
- Регистрация методиста не логинит сразу: требуется подтверждение администратора.
- Роль при публичной регистрации жёстко `METODIST` (нет инъекции роли).
- Служебный admin защищён от удаления/блокировки.
- Удаление аккаунта обезличивает связанные попытки (право на удаление).
- Уникальные индексы `username`, `email`, `public_token`.
- Backend и Mongo **не публикуют порты наружу** (только nginx `web`).
- Валидация входных данных с русскими сообщениями.
- CORS отключён для прода (один origin через nginx).
- Изображения валидируются по содержимому (Pillow), с лимитом размера **и разрешения**;
  SVG запрещён; имя файла генерируется; отдача с `nosniff`.
- При неудачном входе логин не раскрывается (bcrypt сверяется всегда).

## 5. Юридические требования (152-ФЗ) — памятка

1. **Уведомление РКН** об обработке ПДн (оператор обязан подать до начала обработки).
2. **Политика обработки ПДн** — опубликована на сайте, доступна пользователям.
3. **Согласие субъекта** на обработку ПДн — реализовано для методистов (регистрация) и
   обучающихся (чекбокс на странице прохождения + проверка на сервере).
4. **Минимизация** — собирать только необходимые данные (ФИО + номер сертификата — обосновать необходимость).
5. **Локализация** — ПДн граждан РФ хранятся на серверах в РФ.
6. **Права субъекта** — доступ, уточнение, удаление, отзыв согласия (реализована часть: удаление аккаунта).
7. **Меры защиты** (ст. 19) — организационные и технические меры (см. чек-лист выше).

> Точные формулировки согласий, политики и основания обработки ПДн несовершеннолетних
> должен согласовать юрист организации-оператора.
